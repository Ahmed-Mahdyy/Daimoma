# Data Model: Request Allocations

**Status**: Implemented (migration 0005). **Amended 2026-10-06 (owner):** the fixed `category` field was replaced by a visible `unit`; employees enter the charged amount directly, so category calculations and the company-workweek dependency were removed. `Organization.working_weekdays` is retained non-destructively but is no longer consumed by allocation logic. All business references carry/validate the same organization as the employee and request type. UUID IDs; organization-local dates for policy evaluation, UTC timestamps for events.

| RequestType | `unit` enum (`none`, `unit`, `hour`), default `none`; `requires_allocation` derived in `save()` as `unit != none`; `code` retained for uniqueness but auto-generated server-side and hidden from the UI | The unit is the allocation switch and decides the employee's amount input: `unit` → positive whole quantity; `hour` → positive quarter-hour hours; `none` → no amount. The unit must not change while grants or commitments exist. Independent of `requires_hr`/routing. |

## Calculation and lifecycle

- `unit` type: the entered `quantity` (positive integer) is the charged amount.
- `hour` type: the entered `hours` (positive, quarter-hour steps) × 60 is the charged amount in whole minutes.
- Grant coverage: the grant's inclusive dates must cover the request's stated `[start_date, end_date]` interval — or the organization's local submission date when no dates were given. One request always draws from exactly one grant; no splitting.
- Granted = `initial_amount + SUM(adjustment.delta)`; reserved = SUM(amount where disposition=reserved); used = SUM(amount where disposition=used); remaining = granted - reserved - used (nonnegative). Released commitments do not subtract. No independent mutable remaining-balance field.
- Draft -> pending: create one reserved commitment after capacity check. Manager -> HR pending: reservation unchanged. Final approval: reserved -> used; rejection/return: reserved -> released. Return then resubmit: new cycle, new validation and commitment. A grant expired after a valid submission retains its pending reservation until decision; expiry only prevents new submissions.
- Request type unit changes do not change existing commitments. Enabling a measurable unit applies to subsequent submission cycles, including a returned request on new submission; never backfill an already pending or approved cycle.

## Integrity and concurrency

- Validate organization consistency in service and model validation; cross-table organization equality cannot be enforced with a simple CHECK constraint.
- CHECK initial_amount>0, delta!=0, commitment.amount>0, grant end>=start; unique request/cycle; indexes on (organization, employee, type, start_date, end_date) and grant/disposition after query-plan review.
- Lock the employee profile first for every capacity mutation; submit then locks request and grant before creating steps, review locks request then steps/commitment, and HR grant changes lock profile then grant. No path takes profile after request/grant; recheck latest grant/version/type/available units inside the same transaction. Adapt existing review/submit services rather than bolt on a separate unlocked after-hook. Database-backed race tests must demonstrate nonnegative availability and no duplicate commitments.
- Audit grant creation, each date edit, amount adjustment, void transition and request-cycle transition without copying sensitive free-text employee payloads. Only an active grant with zero reserved and used amounts can be voided; a voided grant and its released history remain in HR's scoped history. Never delete grants, change events or commitments as a means of correcting a balance.

## Migration and backfill

Additive migrations only. Migration 0005 replaced `RequestType.category` with `unit` and remapped populated data: allocated date types → `unit`, early leave → `hour`, unallocated types → `none`; grant/commitment units remap `working_day`/`item` → `unit` and `minute` → `hour`. `EmployeeRequest.hours` added nullable. Existing requests retain their lifecycle with their original commitments; `working_weekdays` is retained but unused by allocation logic. No production change is authorized at planning time.
