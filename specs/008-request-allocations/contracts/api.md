# Proposed Allocation API and UI Contract

**Planning only.** Same-origin authenticated `/api/v1/` requests, session/CSRF protections, organization scoping and safe errors from 002/003. `org`/`employee` on writes are resolved or checked server-side; clients never write `remaining`, commitment disposition or approval status. All grant lists are paginated with allowlisted filters and deterministic ordering; invisible IDs return 404, HR-only changes by non-HR return 403, invalid inputs 400, stale versions 409.

| Route / integration | Input | Response and authorization |
| --- | --- | --- |
| GET/POST `request-types/`, PATCH `request-types/{id}/` (existing) | `unit` (`none`/`unit`/`hour`, default `none`), name, help text, approval-stage flags | HR write only; `code` auto-generated server-side and read-only; `requires_allocation` derived from `unit`; reject unit changes with grants/commitments; the unit is visible on read. Approval-stage flags are independent. |
| GET `allocations/mine/` | Optional page/status filter | Authenticated self only: paginated active grants with type, unit, inclusive dates, granted, reserved, used, remaining; no-grant represented explicitly in dashboard choices. Includes expired active grants with pending commitments as labeled history; voided grants never appear as available capacity. |
| GET/POST `allocations/` | HR list filters scoped to org, including active/void status; POST employee ID, active type ID, inclusive start/end, positive integer initial amount, unit derived from type | HR-only org-scoped paginated list/create; no cross-org employee/type, no overlaps among active grants for the same employee/type; history remains searchable after removal. |
| GET `allocations/{id}/` | ID | HR reads scoped org detail including status, dates and totals; separate paginated history endpoints below provide audit/adjustment entries. Employee reads own active detail only. No other employees' free-text requests. |
| PATCH `allocations/{id}/` | HR-only: inclusive start/end dates, nonblank reason, expected grant version | Recheck overlap and all reserved/used commitment coverage under locks; audit old/new dates with actor/time and increment version. Employee/type/unit/initial award and computed balances are not PATCHable; released history remains. |
| GET `allocations/{id}/adjustments/`, GET `allocations/{id}/changes/` | Page | HR-only scoped, paginated append-only adjustment and date/removal event history. |
| POST `allocations/{id}/adjust/` | Signed nonzero delta, nonblank reason, expected grant version | HR-only; audited adjustment, version increments; granted amount cannot go below reserved+used; no direct PATCH on computed amount. |
| POST `allocations/{id}/void/` | HR-only: nonblank reason, expected grant version | Remove from active use, not database: only allowed with zero reserved and zero used amount under locks; record actor/time/reason and increment version; retain released history. Already-void or stale attempts return 409. No DELETE endpoint. |
| GET `requests/allocation-preview/` | type, the type's amount (`quantity` for `unit`, `hours` for `hour`), optional dates/times | Employee own estimate and unit, possible grant/remaining or `no_grant`/`insufficient`; does not reserve and is not authoritative at submit; no other employee argument. May be omitted if equivalent scoped request-form data supports a reliable preview. |
| POST `requests/{id}/submit/` (existing) | expected request version | Recalculate under locks, validate single eligible grant, create one commitment for new cycle; preserve existing reviewer resolution/events/notification. Error includes safe field/detail code, no grant identifiers for others. |
| POST `requests/{id}/{approve,return,reject}/` (existing) | existing version/reason | Existing reviewer permissions; final approve moves reserved to used, return/reject release; manager approval advancing to HR leaves reservation unchanged. Idempotency/stale semantics unchanged. |
| GET `dashboards/personal/` (existing) | Existing optional date filters | Add `allocations` collection representing *currently relevant* own active grants and expired active grants with pending reservations, each with type, unit, period, granted/reserved/used/remaining and `expired` flag; voided grants are not displayed as active capacity. Independent of dashboard request report date window. Team/org responses do **not** include individual allocation values. |

### Semantics and response example

A grant of 10 units with 3 used and 2 reserved yields `{ "granted": 10, "used": 3, "reserved": 2, "remaining": 5, "unit": "unit" }`. Hour grants store and return whole minutes — `{ "granted": 240, "unit": "hour" }` is four hours; the UI formats it as hours. Dates are inclusive ISO dates evaluated in organization time zone; timestamps carry offsets. `unit` requests charge the entered positive integer `quantity`; `hour` requests charge the entered positive `hours` (quarter-hour steps) as whole minutes. Grant coverage uses the request's stated inclusive date interval, or the org-local day of the successful submission transaction when no dates were given. A request draws from exactly one grant; no splitting. Dated grants never auto-renew. Expired pending reservations remain reserved until a decision, but expired grants are unavailable to new requests. Never sum across different units or different grant periods as if they were interchangeable.

### UI and security contract

HR: per-type unit selector (`none`/`unit`/`hour`) with no `code` field; searchable/sortable/paginated active and voided employee allocations table, detail/history view, dedicated `/settings/allocations/new` grant page (employee + type + amount in the type's unit + inclusive dates), date-edit/adjust/remove-from-active-use controls with reason, safe concurrent-update errors and visible removal confirmation. Employee: form preview with unit and insufficient-grant feedback, personal dashboard breakdown/empty and expired states. Read-only managers see their own personal balances, not their reports' grants. Protect generated API/schema and browser cache by identity; invalidate personal dashboard after submit/decision/adjustment and clear on logout. EN/AR RTL labels, keyboard controls, 320px reflow and WCAG 2.2 AA checks. Do not show unavailable grant as a zero awarded balance.
