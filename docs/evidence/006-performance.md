## Real defect found and fixed

`GET /api/v1/timesheets/` serialized nested `days`+`entries` per list row with
no prefetch — on the 500-employee dataset it measured **p95 13,269ms** under
25 concurrent users. Fix:

- New `TimesheetListSerializer` drops the nested `days` field from list rows
  (the list UI never rendered them; detail responses unchanged).
- `timesheet_queryset` annotates `total_minutes` via a filtered `Sum` and
  `select_related`s `current_reviewer__profile`.
- Result: **p95 201ms** (66x improvement), constant query count.
- Regression guard: `test_list_bounded_queries` now builds 12 sheets and keeps
  the ≤15-query budget — the previous 6-sheet fixture passed even with the N+1.
- Schema: both components share `TimesheetStatusEnum` via
  `ENUM_NAME_OVERRIDES` — 0 spectacular warnings; `schema.d.ts` regenerated.

## UI redesign re-measurement (2026-10-02)

After adding shadcn/ui and lazy-loaded calendar/dashboard and reports, `vite build`
produced an initial JS chunk of **180.92 KB gz** on the final build, dashboard chunk **23.64 KB gz**,
reports chunk **2.34 KB gz**, CSS **15.35 KB gz**. Initial JS remains below the
500 KB gz budget; Vite warns about the 573 KB **uncompressed** initial chunk.

The same 25-session / 4-round gunicorn workload was re-run after the UI changes:
me 129ms, timesheet list 185ms, personal dashboard 167ms, hours report 158ms,
requests report 152ms, notifications 143ms at p95; **0/600 errors**. All approved
read budgets pass on the same development stack. This does not measure
production browser Web Vitals or write-path load.
